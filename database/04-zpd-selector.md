# Qudrat AI Tutor — Phase 1: ZPD Next-Lesson Selector (v1, rule-based)

**Requirement traced:** FR-03 — "ZPD-driven next lesson recommendation, explainable in one sentence to the student."
**Brief instruction:** "Start simple (rule-based over the syllabus graph) and document how it could evolve."

This is a pure function of the data model already seeded (`skills`, `skill_prerequisites`, `learning_records`, `srs_state`). No new tables needed — this is service-layer logic.

---

## 1. What "Zone of Proximal Development" Means Here, Concretely

A skill is in the student's ZPD right now if:
- She has **not yet mastered it** (no active `mastery` learning_record for it), **and**
- She **has** mastered everything it directly depends on (every `prerequisite_skill_id` has an active `mastery` record).

That's "reachable, not yet done" — too easy (already mastered) is excluded, too hard (prerequisites missing) is excluded, by construction.

---

## 2. Selection Algorithm (v1)

Runs per student, on demand (when she asks for her next lesson) or nightly (to precompute the day's recommendation).

### Step 1 — Build the mastery set
```
mastered_skills = { skill_id | active learning_record with record_type = 'mastery' for this student }
```

### Step 2 — Build the ZPD candidate pool
```
zpd_candidates = { skill in skills
                    | skill.id NOT IN mastered_skills
                    AND ALL prerequisites of skill ARE IN mastered_skills }
```
(A skill with zero prerequisites is automatically eligible once no mastery record exists for it — this is how the graph "starts".)

### Step 3 — Priority ordering within the candidate pool

Priority is evaluated top-down; the first rule that produces a non-empty result decides. This directly encodes your own Discovery Report's Lesson 0001→0002→0003 sequence (§3.6).

**Priority 1 — Due retests (tentative corrections).**
```
retest_pool = { skill in zpd_candidates
                | active learning_record for this skill has
                  record_type = 'misconception_corrected'
                  AND confidence = 'tentative' }
```
If non-empty → pick the retest whose learning_record is **oldest** (don't let a flagged misconception sit too long before confirming it's fixed). This is exactly what happened between your Lesson 0002 and 0003.

**Priority 2 — Spaced-repetition items due today.**
```
srs_due_pool = { skill in zpd_candidates
                 | srs_state.next_review_at <= today for this student+skill }
```
If non-empty → pick the one **most overdue** (`today - next_review_at` largest).

**Priority 3 — Frontier expansion (default path).**
No retest, nothing due → pick the ZPD candidate with the **lowest `base_difficulty`**, breaking ties by **fewest prerequisites** (simplest on-ramp first), then by insertion order (deterministic).

### Step 4 — Generate the one-sentence explanation (FR-03's explicit requirement)
Template, filled from the same data used to select:

- If via Priority 1: *"لأنك صححتِ فهمك في `{skill.name_ar}` سابقًا، نعيد اختبارها للتأكد أنها ثابتة."*
- If via Priority 2: *"حان وقت مراجعة `{skill.name_ar}` حتى لا تُنسى."*
- If via Priority 3, and it has a mastered prerequisite: *"لأنك أتقنت `{prerequisite.name_ar}`، الخطوة التالية المنطقية هي `{skill.name_ar}`."*
- If via Priority 3, no prerequisites at all: *"هذه نقطة بداية جيدة في `{skill.category}`."*

This is stored alongside the recommendation, not regenerated by the LLM — it must be traceable to the actual rule that fired, not a plausible-sounding LLM paraphrase, since a wrong explanation would be as trust-damaging as a wrong answer key.

## 3. Reference Implementation (pseudocode → real SQL, service layer in TypeScript)

```sql
-- Step 1 & 2 combined: candidate ZPD skills for a given student
with mastered as (
  select skill_id from learning_records
  where student_id = $1 and record_type = 'mastery' and status = 'active'
),
zpd_candidates as (
  select s.id, s.name_ar, s.base_difficulty, s.category
  from skills s
  where s.id not in (select skill_id from mastered)
    and not exists (
      select 1 from skill_prerequisites sp
      where sp.skill_id = s.id
        and sp.prerequisite_skill_id not in (select skill_id from mastered)
    )
)
select * from zpd_candidates;
```

```sql
-- Priority 1: due retests among the candidates
select lr.skill_id, lr.created_at
from learning_records lr
join zpd_candidates zc on zc.id = lr.skill_id   -- (CTE reused via application layer, not literally chained in one query)
where lr.student_id = $1
  and lr.record_type = 'misconception_corrected'
  and lr.confidence = 'tentative'
  and lr.status = 'active'
order by lr.created_at asc
limit 1;
```

```sql
-- Priority 2: SRS-due among the candidates
select srs.skill_id, (current_date - srs.next_review_at) as days_overdue
from srs_state srs
join zpd_candidates zc on zc.id = srs.skill_id
where srs.student_id = $1
  and srs.next_review_at <= current_date
order by days_overdue desc
limit 1;
```

```sql
-- Priority 3: frontier expansion — lowest difficulty, fewest prerequisites
select zc.id, zc.base_difficulty, count(sp.prerequisite_skill_id) as prereq_count
from zpd_candidates zc
left join skill_prerequisites sp on sp.skill_id = zc.id
group by zc.id, zc.base_difficulty
order by zc.base_difficulty asc, prereq_count asc
limit 1;
```

The service layer runs these three in order and short-circuits on the first non-empty result — matching the "first rule that produces a non-empty result decides" spec above.

## 4. Edge Cases Worth Deciding Now

| Case | Resolution |
|---|---|
| Brand-new student, no learning records at all | `mastered = {}`, so every zero-prerequisite skill is a candidate → Priority 3 picks the lowest-difficulty one across *both* sections. Confirm: should Day 1 mix verbal + quantitative, or does the diagnostic decide a starting section? *(flagging — see open question below)* |
| Two skills tie exactly on difficulty and prereq count | Order by `skills.created_at` (insertion order in the seed) for determinism — avoids the recommendation flapping between two equally-valid choices on repeated calls. |
| A skill has prerequisites from *both* sections (e.g., a quantitative skill needing a verbal one — not expected in current graph, but schema allows it) | No special handling needed; the graph traversal is section-agnostic by design. |
| Mission is superseded mid-program (target score changes) | Selector is unaffected — it reads `learning_records`, not `missions`, directly. Mission changes affect *pacing/urgency* messaging, not skill selection. Worth revisiting once §Phase 2 pacing logic exists. |

**Open question for you:** should the diagnostic assessment (next piece of work) pre-seed *some* learning records so the very first ZPD call isn't choosing from the entire 44-skill frontier at once? (Recommended: yes — diagnostic performance should seed initial `mastery` records for skills answered correctly with high confidence, so Day 1 already has a meaningfully narrowed ZPD.) Flagging this now because it changes what the **Diagnostic Assessment** piece needs to produce.

## 5. How This Evolves Past v1 (per the brief's "document how it could evolve")

- **v2 — weighted scoring instead of strict priority tiers.** Replace the three hard priority buckets with a single score per candidate: `w1 * retest_urgency + w2 * srs_overdue_days + w3 * (1/base_difficulty) + w4 * mission_time_pressure`. Requires the `missions.exam_date` and `weekly_study_hours` fields already in the schema — no migration needed, just new logic.
- **v3 — mastery as a continuous estimate, not a boolean.** Right now "mastered" = "has an active mastery learning_record." A richer model would compute a mastery *probability* per skill (e.g., Bayesian knowledge tracing over `attempts` + `srs_state`), letting "prerequisite satisfied" be a threshold rather than a binary flag. Schema already stores raw `attempts`, so this is additive, not a rewrite.
- **v4 — cross-student signal.** Once enough students exist, skills that are *frequently* miscorrected across the population could get an elevated default `base_difficulty`, closing the loop between real outcomes and the syllabus graph's authored estimates.

None of these require schema changes now — this is why `attempts` and `srs_state` were modeled as raw signal in Phase 1 rather than only storing derived state.
